# pacs008-loader-mt103 v0.0.12

No parser changes: `parse_mt103` behaves exactly as it did in 0.0.3.
What this release adds is a benchmark, a drift check, and a version
number that agrees with the rest of the suite.

## Why the number jumped from 0.0.3

The `pacs008` suite ships **one version number across all three
packages** by policy, and it had drifted badly: `pacs008` at 0.0.11,
`pacs008-mcp` at 0.0.9, and this loader at 0.0.3.

Nothing breaks when that happens, which is exactly the problem. A member
left a release behind still installs, still imports, and still passes its
own tests. Only the index disagrees, and only if somebody looks.

All three now sit on **0.0.12**.

## A benchmark, and what it refuses to measure

`benches/bench_parse_mt103.py` measures the cost of one call — because
there is no batch axis here, and the obvious benchmark would be
misleading.

An MT103 carries exactly one customer credit transfer. Concatenating two
of them and parsing the result returns **one** record: the second is
dropped silently, not rejected. A throughput curve built on concatenated
input would show per-message cost falling as the file grows, which looks
like batching and is the opposite — the cost falls because it is divided
by messages that were never parsed.

The benchmark asserts this rather than only describing it. If the loader
ever grows multi-message support, the output says its framing needs
revisiting.

| case | cost |
| :--- | ---: |
| complete message | ~6.2 µs |
| block-4 envelope (`{4:...-}`) | ~7.3 µs |
| rejected (bad `:32A:`) | ~3.2 µs |

Roughly **150,000 messages/second**, one call per message.

Two details worth having on the record. Real SWIFT traffic arrives inside
a block-4 envelope, so that form is timed separately — unwrapping costs
about a microsecond. And **refusal is cheaper than success**: the
mandatory-field check fails before the field parsers run, which is the
right way round for a tool that exists largely to find malformed
messages.
